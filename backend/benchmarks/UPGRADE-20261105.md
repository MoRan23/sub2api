# Integrity, telemetry and Images changes: rollout notes

## Scope

Request integrity retains the same enablement, observation fields, redaction,
8 MiB limit, duplicate-key checks, depth/node limits and message alignment.
Each physical send still invokes the checker. Only a byte-for-byte match with
its validated frozen baseline can skip reparsing; all changed outbound bodies
are fully validated. Shared baseline containers are immutable, and timezone
equivalence uses the already frozen patch group.

Telemetry activities keep their existing table and JSON formats. Transactions
read related keys, stage explicit changes, and query transient capacity and
expiry inside PostgreSQL. Permanent thread initialization markers are retained.
Maintenance processes up to 128 due active turns per pool transaction; remaining
records continue to determine the pool's next due time. Identity, policy fences,
batch delivery states, retention and sampling deduplication are unchanged.

Migration `275_codex_telemetry_activity_queries.sql` adds two partial indexes:
pool-local due activity lookup, and transient activity age/capacity queries.
It does not rewrite JSON or introduce persisted counters.

OAuth Images generation/edit routing now recognizes the exact model IDs
`gpt-image-2.6-sunburst` and `gpt-image-2.6-flare`, after model mapping, using the
existing native Images adapter. Existing 2.5 behavior, prices and account model
authorization remain unchanged. The existing Images request parser does not
carry an independent `complexity` parameter; that separate issue is not changed
here. Quality/complexity translation is not introduced. Actual image output and
supported parameter values require a separately authorized post-deployment test.

## Upgrade

1. Preserve the current executable/container reference and take the normal
   database backup before a scheduled rollout.
2. Stop admitting new work to old instances and drain their active requests and
   telemetry transactions. Shut down all old processes before switching this
   telemetry transaction implementation; do not perform a mixed-version rollout.
3. Start the new version with the usual migration mechanism. The extra indexes
   are created on existing rows; budget a maintenance window proportional to
   the activity table size. No manual record deletion or reset is required.
4. Start all instances on the same version and restore ingress. Verify that
   telemetry maintenance advances, batches retain their existing send/retry
   states, and account deletion cleanup continues to make progress.

This task only changes and tests local code. It does not perform these deployment
steps, change production data, or call a real image/model upstream.

## Rollback

Drain and stop the new processes, then restart all instances with the previous
version. The activity/batch format remains compatible. Keep both new indexes and
the migration history; no reverse migration or historical JSON rewrite is needed.

## Observe after deployment

Compare periods with similar request sizes, concurrency and retry rates:

- Go allocated bytes, live heap, GC frequency and process memory.
- Integrity latency and the distribution of status/reason/rule/path observations.
- Telemetry transaction latency, activity rows/bytes returned, oldest due age,
  pending batches and pool-cleanup progress.
- Request latency/error rate and usage recording completion.

See [PERFORMANCE-20261105.md](PERFORMANCE-20261105.md) for synthetic measured
results and exact reproduction. Report same-body and transformed-body cases
separately, and compare sampled memory peaks as samples rather than guarantees.
