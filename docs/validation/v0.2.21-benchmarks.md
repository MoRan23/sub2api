记录日期：2026-11-11。本文保留固定三轮初测数据，并单独记录针对耗时异常场景的复测；不把不同运行参数的结果混为一组。

**最新结果：`c42a3e842` 的局部图片字段视图修复已完成。** 在相同 P=4、交替三轮的无 profile 复测中，32 MiB WebSocket 为 **237.006 → 245.688 ms/op（+3.66%）**，同轮变化为 -0.62%、+3.66%、-0.18%，分配仍为 **111 allocs/op**，B/op 无增加。四个小消息 relay 中位数改善 **2.41%–6.14%**，分配次数与基线一致。这五项最新定向测量未再出现超过 5% 的耗时回退。

此前审计 off 的额外分配已降为固定 **+16 B/op、分配次数不变**。缓存 50%/100% 共享场景在较长固定次数的 CPU 采样运行中未延续早先的耗时回退，短样本与传输波动证据保留在文中。下面按阶段完整记录初测、复测、profile 定位和最终修复；旧的 +6.76% 属于字段视图修复前数据。

## 初测主要观察

- 审计 `off` 的所有请求大小均从 **896 → 928 B/op、4 → 5 allocs/op**，即固定增加 32 字节和一个分配；分配次数相对增加 25%，字节数增加 3.57%。增加量不随 64 KiB–8 MiB body 增长。
- 未命中的关键词/组合路径多见少量固定分配增长。例如 image 64 KiB keyword 为 +96 B/op、+2 allocs/op，text 8 MiB combination 为 +96 B/op、+2 allocs/op。大输入有少量每轮内存采样变化，详细值保留在表中。这里观察到的是固定小对象和运行波动，没有新增一整份 body 拷贝的大小特征。
- Relay 的 1/8/32 MiB terminal，HTTP 分配字节中位数仅分别增加 **158/96/96 B/op**；8 MiB HTTP/WS 均为 +96 B/op、+2 allocs/op。原有 terminal 大量分配仍在，不能把“小增量”写成“总分配很少”。
- TopK 六个场景的 B/op 和 allocs/op 完全相同，耗时仍有 +4.01%–+19.98% 的中位数差异，提示机器状态和时间批次值得控制。
- HTTP/WS `small_256` 耗时中位数分别增加 **46.94%/49.42%**，`multiline_128` 分别增加 **35.80%/34.52%**。这些场景三轮的取值范围完全分离，需要优先复测和定位，不能统一归为噪声。

`BenchmarkPromptAuditMemory` 使用合成安全文本/图片数据；keyword 和 combination 场景均不命中，也未装配数据库处罚仓储。这组结果衡量提取/匹配/关闭路径，不包含处罚入库、SMTP 发送或 Redis 往返。`snapshot` 直接调用 `ExtractPromptSnapshot`。原始 `MB/s` 按整个 body 大小计算，`off` 未扫描 body 的巨大数值不作为吞吐量结论。

## 固定分配增量定位

对 `Audit/text/65536/off` 使用原始两个二进制，各执行 `-test.benchtime=10000x -test.memprofilerate=1 -test.memprofile=...`，通过 `go tool pprof -alloc_space/-alloc_objects -list='cloneActiveConfig|CheckKeyword'` 定位。profile 运行只用于分配归因，不并入耗时表。

- 修复前，`prompt_config_store.go` 的 `cloneActiveConfig` 新增 `JailbreakKeywords` 副本。本 fixture 有一个词，每次增加 16 字节、一次分配；10,000 次累计 156.25 KiB。原有 `BlockedKeywords` 副本仍然存在。定位后已将分类列表及其兼容投影共用一份请求快照内的克隆，保留 legacy-only 与显式清空语义，见最终复测。
- `prompt_types.go` 的 `PromptDecision` 新增 `Enforcement` 指针后，关闭路径返回的允许结果对象由每次 48 字节的分配档位变为 64 字节。对应 `CheckKeyword` 的 10,000 次累计分配从 468.75 KiB 变为 625 KiB，增加 16 字节但不增加分配次数。
- 两处恰好解释 **+32 B/op、+1 allocs/op**。关闭路径没有新增 body 解析或复制；新增 Request 字段和 UUID 生成不是这个 benchmark 的分配来源。

进一步只读比对两个二进制的 `gjson.parseSquash` 汇编：两者均为 **229 条指令、864 字节**，归一化函数内跳转地址后，源码行、相对偏移和指令序列 **零差异**。16 处机器码差别均为全局表或 runtime panic 函数的重定位。函数入口从 `0x14065f800`（mod 64 = 0）变为 `0x14065fe20`（mod 64 = 32），原有热循环的地址对齐位置改变。

这使既有热点的链接布局变化成为具体、可验证的候选原因；确认其因果关系仍需只改变布局、保持语义与输入完全相同的 A/B。当前结论是“CPU 增长已经定位到既有 JSON 扫描热点，布局有差异”，没有将它写成新的扫描逻辑回退或已证明的唯一原因。
