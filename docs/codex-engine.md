# Codex-Engine 接入

在账号管理中创建或编辑 **OpenAI → API Key** 账号，将“接入模式”设为 **Codex-Engine**，填写 Engine Key 和 **Codex-Engine 平台 API** 地址。不要填写 Worker 直连地址：Worker 不提供完整的 Chat、Messages 和 count_tokens 入口。

地址支持部署路径前缀、尾斜杠和已有 `/v1`，例如 `https://engine.example/prefix/v1`。模式保存在 `extra.openai_api_key_mode`，值为 `generic` 或 `codex_engine`；旧账号未设置时仍使用通用模式。账号导入导出会保留模式，无需数据库迁移。

专用模式复用 Sub2API 的鉴权、分组权限、模型白名单与映射、速度策略、并发、限额和记账。普通透传及协议兼容设置在此模式下不参与转发。Responses（包括 compaction_trigger）、Responses compact、Chat Completions、Messages、独立搜索、图片生成/编辑和 Messages count_tokens 均转发到平台同名接口，由 Engine 处理协议转换。count_tokens 继续不计费。

开启全局“订阅优先”时，Codex-Engine 账号与 OpenAI OAuth 订阅账号共同进入首选调度池，按原有账号优先级和负载评分选择，不因 API Key 认证方式被放到普通 API Key 后备池。账号类型、认证和计费方式保持 API Key。

Codex-Engine 模式自动同步账号并发上限：服务启动立即检查，之后每分钟使用该账号的 Engine Key 请求 `GET /v1/engine/capacity`；新建或改为 Engine 模式的账号在下一轮开始同步。地址仍支持路径前缀和已有 `/v1`，请求使用该账号代理及现有出站地址策略，不跟随重定向。各账号独立推进，慢账号不会阻塞其他账号；关闭调度的账号仍继续读取容量。

响应的 `object` 为 `codex_engine.capacity`，`concurrency_limit` 表示这个 Key 所在分组的可用账号配置并发之和，不减去正在使用的槽位。例如 20 + 10 返回 30，其中 10 并发的账号限流后返回 20；两者都不可用时返回 0。正值同步账号实际并发设置；0 会关闭该 Sub2API 账号的实际调度，并保留之前的正数并发设置，避免将 0 解释为无限。稍后恢复正值，仅恢复本同步关闭的调度；管理员手动暂停（包括再次点击暂停）会撤销自动恢复权限。减小并发不会中断已在执行的请求。

仅容量或实际状态变化时保存并更新调度缓存。网络错误、401、404、5xx 和无效容量响应保留最后有效状态，旧版 Engine 暂未提供接口时也沿用当前设置。返回途中发生 Key、地址、认证类型、代理、接入模式或人工调度修订变化时丢弃旧结果。Engine 模式内修改连接配置不会立即恢复调度，须由新连接成功返回正容量后才恢复本同步拥有的暂停；退出 Engine 模式则清除自动恢复权限，已关闭的调度交由管理员处理。容量查询只读取状态，不发送模型探针，不占业务调用槽；这项同步不修改已有用量和账单。

配置并启用全局自动归因检测后，Codex-Engine 账号还需开启账号编辑页的「自动归因检测」开关，才会每 10 分钟参加周期检测。该开关与普通 OpenAI API Key 共用 `extra.openai_api_key_auto_attribution_enabled`，默认关闭，旧账号缺失该字段也按关闭处理。关闭只停止后续自动入队，手动测试及已入队任务继续；普通与 Engine 模式切换保留同一偏好。检测沿用全局／分组策略；白名单模式下，账号首次可应用的有效判定立即应用对应名单，之后升级仍需连续两轮通过。停用、关闭调度、过期、影子账号及本地限流仍跳过自动检测；普通透传配置不影响专用模式。新 OAuth 账号首测及鹈鹕测试不扩展到 Engine。详见[降智检测](model-attribution.md)。

JSON 正文保留工具、namespace、历史、密文及未知字段，仅按现有模型映射和速度策略修改必要字段。公开会话、线程、回合与工具关联头会保留；下游认证与 Engine 内部控制头不会转发。Engine 的 JSON/SSE 和业务错误原样返回，业务错误默认不触发账号停用，也不触发兼容降级或跨账号重放。已有用量及图片结算流程继续使用上游实际返回的信息，不估造缺失 token。

Engine 的 Responses／compact 标准 `usage` 统计本次外部请求内所有真实模型采样的用量。Sub2API 原样转发，并按该请求最终确认的用量结算；不会逐帧累加中间统计，也不会把上一请求的用量带入下一请求。缓存输入已包含在总输入中，账单拆分时不会重复相加。例如 `input_tokens=1200`、`cached_tokens=960`、`output_tokens=83` 对应普通输入 240、缓存输入 960、输出 83。沿用标准 `usage` 和既有用量标识，不增加额外计费字段或协商头。

客户端声明的工具及 `tool_choice` 保持原样，Sub2API 不执行工具，也不代填工具结果。客户端执行工具后提交 `function_call_output` 是新的外部请求，独立转发和结算；同一次执行的结果回放则按下述用量标识去重。Engine 的受管工具 RPC 路径应保持客户端工具直接调用，避免模型目录中的 `code_mode_only` 覆盖关闭配置而意外启用 Worker 内置 `exec`／`wait`；客户端声明的同名工具仍交由客户端执行。该边界同时适用于直连 Engine 和经过 Sub2API 的客户端。

显式 `web_search`、Engine 原生自动压缩或尚未结束的原生回合仍可能在一个外部请求内合法地产生多次模型采样。这些内部采样不会分别经过 Sub2API，最终标准用量仍须包含全部实际消耗。修复非预期 CodeMode 调用不改变这类合法请求的统计；Sub2API 不将累计用量截成末次用量、不改写 `total_tokens` 来压低上下文显示，也不从响应内容推算隐藏采样。当前 Codex 将同一个 `usage.total_tokens` 用于上下文判断，成功响应没有独立的上下文用量字段，因此合法多采样仍可能影响压缩判断；本次保持真实计费和标准协议，针对非预期工具调用修复频繁采样的来源。

Engine 连接发生网络错误时，仅在请求追踪确认尚未取得连接、且明确是 DNS 或拨号失败时允许切换账号。取得连接后发生 EOF、连接重置或响应头超时等错误，Engine 可能已经受理请求，Sub2API 记录原网络错误并结束本次转发，不自动重放，也不因此修改账号健康。缺少发送追踪信息的传输同样按可能已受理处理；客户端主动取消沿用原行为。

新版 Engine 为每个已受理请求返回 `X-Codex-Engine-Usage-Id`，格式为 `ceu_` 加 43 个 Base64URL 字符。同一次执行的原响应、并发等待者及重启后的结果回放共用该标识，新的推理轮次使用新标识。Sub2API 仅信任实际选中的 Engine 账号返回的响应头，不采用客户端提供的值；将接入账号 ID 和该标识按固定版本哈希，生成 `ce:` 加 43 个 Base64URL 字符的账务请求 ID，在现有 API Key 账务隔离内去重。用量指纹保存为 64 位十六进制摘要，两者均符合现有数据库字段长度，无需迁移。相同用量的回放不再扣余额、增加额度消耗或新增使用记录，首次成功结算时的价格和账单保持不变；同一标识对应不同用量时记录账务冲突。

用量标识只证明请求已受理，结算还需要完整的终态用量证据。Responses 使用 `response.completed`／`response.incomplete` 的终态用量；Chat 使用最后的完整 usage 加 `[DONE]`；Messages 使用最后 `message_delta` 的完整 usage 加 `message_stop`。终态零值及缺失的可选分项覆盖中间统计。仅收到中间计数就断流，或以 `response.failed` 返回失败时部分用量时，保留原始响应与错误诊断，不提前占用该标识，也不以临时请求 ID 扣款；后续取得完整结果时正常结算。若第一次可见结果本身是回放，也仍会执行首次结算。旧版 Engine 没有有效标识时保留原计费行为，普通 API Key 和 OAuth 不使用此标识。图片、压缩、独立搜索和 token 计数不携带该标识，沿用各自原有规则。

管理员显式开启的「临时不可调度」规则也适用于 Engine 账号，包括池模式。实际 HTTP 错误状态，或 HTTP 2xx 错误事件明确报告的状态码，与任一关键词匹配后，按配置暂停整个账号或对应调度模型；例如 `503` 加 `unavailable`、账号级 30 分钟，会处理 `capacity_unavailable`。只匹配上游实际错误字段（或非 JSON 错误正文），不扫描生成内容，也不使用补造的诊断状态码命中规则。临时状态沿用数据库、调度缓存及到期恢复机制，不修改管理员的调度开关；手动关闭的账号到期后仍保持关闭。自定义错误码策略开启时，沿用其覆盖临时规则的优先级。未开启规则或未匹配时保持原行为。

当 Engine 返回 HTTP 503、错误代码为 `deployment_maintenance` 或 `capacity_unavailable`，且上游响应头明确给出 `X-Codex-Engine-Unavailable-Scope: deployment` 时，当前 Sub2API 进程暂时跳过该接入账号，后续独立请求按现有分组权限选择其他可用账号。冷却采用 `Retry-After`（秒数或 HTTP 日期），限制在 1～30 秒，缺失或无效时为 5 秒；到期后重新允许调度，既有成功响应不会提前解除冷却。该状态不写入账号健康或管理员调度设置，不扩散到同地址的其他账号；多实例分别根据各自收到的响应生效。

当前失败请求仍原样返回，不因冷却重放。没有明确 `deployment` 范围的容量错误、其他错误码以及 HTTP 200 流内报告的 503 均不触发该冷却；客户端请求头不能声明这个范围。冷却后没有其他可用账号时，沿用 Sub2API 的无可用账号响应，不主动探测或发送模型请求。

内部归因检测和鹈鹕测试不触发上述临时停调规则，也不建立、延长或清除业务请求产生的部署冷却。隔离依据是内部账号副本的诊断标记，客户端不能通过请求头或正文开启。诊断仍保留上游原始错误、`Retry-After` 及实际用量，每次尝试只发送一次；503 等待由归因任务自身处理，不改变普通业务请求的冷却规则。

排查失败时，在运维错误记录查看上游请求 ID、错误代码和消息。HTTP 200 的 SSE 也可能以 `response.failed` 结束；这类失败会被记录为错误，客户端仍收到上游原始事件。没有实际 token 或图片用量的业务拒绝不生成普通使用记录；失败前已有用量时，是否结算遵循上述用量标识和终态规则。错误诊断只记录错误字段，不额外存储生成内容或请求历史。

Engine 返回结构化 `error.code=cyber_policy` 或 `response.error.code=cyber_policy` 时，接入现有专用风控记录和会话屏蔽，受既有审计分组范围及仅记录设置约束；不通过拒绝文案猜测分类。HTTP 400 的原错误 JSON 直接透传；已开始的 SSE 应以 `response.failed` 返回原错误，`response.error.status_code=400` 用于记录语义状态，HTTP 200 不变。Engine 原生错误类型可映射为 `invalid_request_error`。失败前的真实用量（包括缓存明细）只结算一次；未报告的用量不估造。该拒绝默认不触发账号冷却，也不触发切号、协议降级或重放；管理员显式配置的临时停调规则仍按前述规则匹配。

Engine 负责退役其持有的失败模型 WS，并向 Sub2API 交付结构化失败终态；关闭模型连接本身不能代替向客户端交付错误。Sub2API 自身的 WS 转发收到精确 `cyber_policy` 后先交付拒绝，再结束对应连接，失败上游连接不回池复用。即使该错误同时携带限流或认证失败特征，也不进入自动恢复或换号重试。

即使 `response.failed` 在错误字段前包含大量输出，诊断仍使用专用转发器从完整事件提取并脱敏的错误摘要，避免日志捕获上限把具体原因覆盖为 `upstream stream failed`。摘要沿用现有状态码和错误类型分类，不扩大正文留存范围；发给客户端的 SSE 保持原样。

流式请求在客户端断开或下游写入失败后停止写入，继续读取上游终态和真实用量，沿用现有结算流程，不重放请求。收集阶段的最长窗口使用已配置的流数据间隔超时，心跳不会延长该窗口；配置为零时保持禁用超时。正常连接仍按原有首输出及流空闲超时处理；成功或失败终态到达后立即结束。收集窗口耗尽与首输出超时分别记录，缺失用量不推算为真实消耗为零。

专用模式不会修正历史项 ID、删除密文或去掉 `previous_response_id`。`context_owner_unknown` 表示 Engine 无法确认密文历史归属；`invalid_id_prefix` 或 `unsupported_persisted_item_context` 表示上游拒绝了历史项或无法续接已存储上下文。应结合 Engine 日志处理具体原因；既有不兼容历史需要客户端开始新会话或提供可重放的有效历史，重复发送同一请求通常不能恢复。

图片 JSON 参数原样保留。multipart 图片按上传顺序转为 `images[].image_url` data URL，保留内容及 MIME 类型；单个上传项超过现有 20 MiB 限制会明确报错，请求整体大小限制仍生效。`n`、尺寸、质量等显式参数不会自动改写为 Engine 支持的值；不支持的参数由 Engine 返回错误。转换后不上传或执行任何用户文件。

`/models`、`/model-catalog` 仍由 Sub2API 管理。本模式不提供响应读取/删除、`/capabilities` 或 WebSocket 专用适配。
